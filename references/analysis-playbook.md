## 一、方法从哪来（借思路，不接服务）

用户研究这块借的是**方法套路和写作规范**，不是接了谁家的系统，也没复用谁的代码。

| 方法 | 大白话 |
|---|---|
| 主题分析六步法 | 熟悉材料 → 初始编码 → 找出主题 → 回头评审 → 精炼打磨 → 带证据写报告 |
| 亲和图 | 把相似的原话贴成几堆，再给每堆起名 |
| 三角验证 | 同一结论用不同方法 / 不同来源 / 不同时间各验一遍 |
| persona（用户画像） | 把一类人写成一张典型人物卡 |
| 影响力-工作量矩阵 | 按「影响大不大 / 做起来难不难」摆四象限排优先级 |
| JTBD | 「玩家其实是想拿这游戏办成什么事」 |
| 机会点排序 | 给每个待改进的点打分排先后（第七节展开） |

设计时参考了公开的用户研究、主题聚类与证据核验方法：**只借通用结构与规范，不接入外部商业服务，也未复制第三方代码或素材**。

## 二、九步分析链路

一步步走，每步都要说清输入、产出、护栏。**顺序不能跳**，尤其第 3 步「先定 slice」必须在聚类之前。

| 步 | 做什么 | 输入 | 输出 | 护栏 |
|---|---|---|---|---|
| 1 | 统一 schema | 各渠道原始数值 + 评论 | 统一字段的两类行（`metric` / `review`） | 原值入库，一个系数不乘；格式见 `data-schema.md` |
| 2 | 清洗去重 / 空结果告警 | 统一后的行 | 干净数据 + 告警清单 | 空结果如实告警，不伪装；模板见 `collection-playbook.md` |
| 3 | **先定 slice** | 干净数据 | 一组切片定义 | **切片先于聚类**，防止「先聚完类再回头找差异」挑结论 |
| 4 | 向量化 | 评论原句 | 数字向量 | 中文默认字符 n-gram（`char_wb` 2–4），零依赖纯 CPU |
| 5 | 聚类 | 向量 | 主题簇 + 代表原句 | **离群点单列为 `-1`**，不硬塞进某个主题 |
| 6 | LLM 主题命名 | 主题簇 | 主题名 + 显式纳入 / 排除标准 | 名字只是索引不是事实；标准模板见 `anti-hallucination.md` |
| 7 | 回溯原句佐证 + grounding 校验 | 主题 + 原句 | 可定位的佐证据 | 查不到 `review_id` 整条丢弃并写审计，见 `anti-hallucination.md` |
| 8 | 量化占比 + 交叉矩阵 + 小样本警告 | 校验后的数据 | 占比表 + 矩阵 | 分母 + 绝对条数 + 小样本警告 + 0 组 + 未指明桶，见第五节 |
| 9 | 三段式洞察与运营动作 | 全部产出 | 报告 | 严格分「数据事实 / 模型推断 / 运营建议」，见 `anti-hallucination.md` |

> `slice`（切片）大白话：按渠道、评分段、版本、时间窗等把评论切成一格一格，比较的是格与格之间的差异。

## 三、用户分层三层维度

按「这个维度有多少字段撑着」分三层，**越往下越靠推断**。

| 层 | 维度 | 可靠性 | 标注要求 |
|---|---|---|---|
| **结构层** | 渠道 / 国家语言 / 版本 / 时间窗 / 评分段 / 游玩时长 / 是否有开发者回复 | 客观、最可靠 | 直接写「依据 `xxx` 字段」 |
| **态度层** | 情感极性、诉求类型、紧迫度 | 推断 | **必须标注为推断** |
| **行为层** | 评论影响力 + 参与度 + 时长（三轴） | 半客观 | 说明每轴取自哪个字段 |

两条铁律：

- [ ] **分层结论必须写「依据哪个字段」**；没有字段支撑的画像，一律标「假设，待验证」。
- [ ] **不要为了显得专业硬套 RFM**：评论数据通常**没有稳定用户 ID、也没有交易金额**，RFM（最近 / 频次 / 金额）会退化成空架子，改用上面「影响力 + 参与度 + 时长」三轴更诚实。

## 四、五套交叉矩阵

**最低可用集**（五套都要有），可再加一套：

- [ ] 渠道 × 主题
- [ ] 评分段 × 主题
- [ ] 版本 × 主题
- [ ] 时长段 × 主题
- [ ] 时间窗 × 主题
- [ ] （可加）人群 × 主题

每格都带绝对条数 `count`、分母 `denom`、占比，样本不足的格标「仅供参考」。

## 五、量化 10 纪律

| # | 纪律 |
|---|---|
| 1 | 一条评论**允许多标签**，禁止强制单簇 |
| 2 | 每个百分比写明**分母**：占全量 / 占该渠道 / 占该评分段，**三者不可混用** |
| 3 | 占比旁**必附绝对条数**（如 `23%（14/61）`） |
| 4 | 样本不足标「仅供参考」，**不给两位小数** |
| 5 | 用「同主题 1–2 星占比 vs 4–5 星占比」作严重度代理（第六节） |
| 6 | 机会点排序 `影响面 × 严重度 × 可行动性 × 商业价值`，**权重显式列出让业务能否决**（第七节） |
| 7 | 趋势须基于**至少两个等长时间窗**（第八节） |
| 8 | **0 组显式显示**，另设「未指明」桶，不许把空组悄悄抹掉 |
| 9 | **小样本警告**：分档规则见 `data-schema.md` |
| 10 | **评论是自选样本，占比只代表评论语料内部结构，不能外推全体玩家比例**（第九节） |

## 六、严重度代理

「这个主题到底有多痛」没有直接指标，用一个**代理**（间接替代量）来近似：

> **同主题在 1–2 星评论中的占比** vs **同主题在 4–5 星评论中的占比**

- 低分里出现得越集中，说明该主题和低分体验越绑定，越值得优先看。
- 这是**代理、不是因果**：只能说「同期出现」，不能说「它导致了低分」。
- 两个占比都要写清分母，且分母口径一致。

## 七、机会点排序公式

```
机会分 = 影响面 × 严重度 × 可行动性 × 商业价值
```

- [ ] **四项权重必须显式列出来**，让业务能看懂、能一票否决；不许塞在黑盒里。
- [ ] 权重是**主观设定**，属于「模型推断」，不是数据事实；报告里要标清、要能改。
- [ ] 排序结果只是**建议**，人工确认后才成为采纳结论（见 `anti-hallucination.md`）。

示例填空（权重由业务定，这里不给死数）：

| 因子 | 权重 | 取值依据 |
|---|---|---|
| 影响面 | `___` | 该主题评论绝对条数 / 占比 |
| 严重度 | `___` | 第六节的低分 vs 高分占比差 |
| 可行动性 | `___` | 是否对应可改的功能 / 运营动作 |
| 商业价值 | `___` | 与预约、留存等业务目标的关联（须人工判断） |

## 八、趋势：至少两个等长时间窗

- [ ] 说「上升 / 下降」必须有**至少两个时间窗**。
- [ ] 两个窗口**必须等长**（同样天数），否则占比不可比。
- [ ] 每个窗口单独给 `count` / `denom` / 占比，样本不足整格标「仅供参考」。
- [ ] 只写「从 W1 到 W2 …同期变化」，不写因果（第十节）。

## 九、自选样本不可外推（报告固定声明）

报告顶部固定放这段，一字不改：

> **评论是自选样本**：愿意写评论的人本就不等于全体玩家。本报告所有占比只代表「这批评论语料内部的结构」，**不能外推为全体玩家比例**。

- [ ] 任何「X% 的玩家觉得…」的说法都违规，必须改成「X% 的评论提到…」。

## 十、报告规矩与措辞模板

### 报告规矩

- [ ] **按口径分组**：`metric_kind`（外显值 / 回传真值）分开、5 分制与 10 分制分开，不可比的不合并算均分。
- [ ] **包含关系不进合计**：整体与其子集不叠加求和，避免重复计数。
- [ ] **列结构定稿别随意增删**：新维度塞进 `note` / `labels` / `topic_*`，别动既有列。
- [ ] **备注只写业务三件事**：从哪来 / 能用多久 / 要不要人确认。
- [ ] **异常区必给下一步动作**：不能只报「有异常」。
- [ ] **按受众裁剪信息密度**：给运营看结论，给复核者看原句与分母。
- [ ] **多端输出口径一致**：Markdown / Excel / JSON **只消费 `ur_report.py::build_rows()`**，不许各算一套。

### 措辞模板（同期出现）

- **只写**：「…与…**同期出现**」「…与…**同期上升**」「…与…**同期下降**」。
- **禁写**：「导致」「因为」「使得」「由于」等因果词。
- 范例：*「渠道 A 评分下滑与『闪退/掉线』主题在低分评论中占比上升**同期出现**」*。
- [ ] AI 起的主题名**只是索引不是事实**（三段式与静态断言见 `anti-hallucination.md`）。
