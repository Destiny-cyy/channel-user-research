# 防臆测护栏（让 AI 起主题名 / 写洞察 / 做人工确认时）

> **什么时候读**：阶段 C 让 AI 起主题名、阶段 D/E 写洞察出报告、以及任何一步需要「人工确认才算数」的时候。分析流程与口径在 `analysis-playbook.md`，字段格式在 `data-schema.md`。

一句话立场：**AI 说的话永远是建议，不是事实。** 报告里每一个数、每一句「玩家怎么说」，都要能翻回原始评论里那一句逐字原话；翻不回去的，整条丢掉，不许留在报告里。

## 一、防臆测 10 护栏（逐条）

| # | 护栏 | 大白话 |
|---|---|---|
| 1 | 每条洞察可回溯 `review_id` + 逐字原句 | 写了「玩家抱怨闪退」，就得能点出是哪条评论、原话是什么 |
| 2 | grounding check 丢弃伪造 / 无法定位的引用 | 引的原话在数据里找不到，整条作废（第二节） |
| 3 | AI 输出永远是建议、人工确认后才成为 finding、append-only 审计轨迹 | AI 起的名、下的结论，人点头之前都只是草稿（第三节） |
| 4 | 主题用**显式纳入 / 排除标准**定义，而非漂亮名字 | 不能只叫「付费劝退」，要说清哪些算、哪些不算（第四节） |
| 5 | 展示 score rationale + 代表样例 + **反例 non-matches** | 说清为什么这么打分，还要给「看着像但其实不算」的例子（第五节） |
| 6 | 小样本警告 / 0 组显示 / 未指明桶 | 别让「没几条」和「没有」混过去（第六节） |
| 7 | 结论后自动追加核查追问 | 每条结论后面跟一串「真的吗 / 还缺什么」，逼人多看一眼（第七节） |
| 8 | 人工抽检 + 编码者间信度 | 抽一批人肉复核，多人打标签要能对得上（第九节） |
| 9 | 保留原始响应 JSON / 请求参数 / 时间戳便于重跑 | 证据链在 `collection-playbook.md`，随时能重跑复核 |
| 10 | 严格区分三段式，报告禁用无来源的精确数字 | 事实 / 推断 / 建议分开，来路不明的「37.2%」不许出现（第八节） |

> `finding` 大白话：被正式采纳的结论。`append-only` 大白话：只往后追加、不回头改的日志，谁改了什么全留痕。

## 二、grounding check 规则

`grounding check`（定位校验）大白话：拿着洞察里引用的 `review_id`，回原始评论库里找那条评论、核对逐字原句是否对得上。

- [ ] 每条洞察必须带 `review_id` + **逐字原句**（不改写、不摘要、不翻译）。
- [ ] **查不到 `review_id`，或原句对不上 → 整条丢弃，并写审计**，绝不进报告。
- [ ] 丢弃也留痕：往 `data/audit/append-only.jsonl` 记一条「什么时间、哪条洞察、因为什么被丢」。
- [ ] 只在**本次语料**里核对，不许拿别的渠道 / 别的时段的句子来凑。
- [ ] 校验由 `ur_report.py --grounding-check` 统一执行，任何出口不得绕过。

## 三、AI 输出永远是建议 + 人工确认 gate

`gate`（闸门）大白话：AI 结论要过一道「人点头」的关，没过就只是草稿。

| 阶段 | 状态 | 能不能进报告 |
|---|---|---|
| AI 刚产出 | `needs_human_confirm`（建议） | 只能放草稿 / 推断段，不能当事实 |
| 人工确认后 | 「已采纳」 | 才可成为正式 finding |
| 每次状态变更 | 写 `append-only.jsonl` 审计 | 谁、什么时候、确认了什么、输入输出指纹 |

- [ ] **AI 输出永远是建议**，人工确认之前不带任何「已定论」口吻。
- [ ] 主题名、洞察、运营建议三类 AI 产出全部走这道 gate，无一例外。
- [ ] 三段式里，「模型推断」「运营建议」两段的 AI 内容都带 `needs_human_confirm`。

## 四、主题用显式纳入 / 排除标准定义

**主题不靠一个漂亮名字定义**，靠「哪些评论算进来、哪些排除」两条清单定义。起个好听名字只是方便检索的索引。

模板（照抄填空）：

```
主题 ID：T__
建议名（仅索引，非事实）：______
纳入标准 inclusion：
  - 原句出现 ______ 类词 / 描述 ______ 情形
  - 且 ______
排除标准 exclusion：
  - 虽提到 ______，但只是 ______ 的，不算
  - 反讽 / 玩梗、无法判断真实诉求的，归「待人工」
代表原句（逐字 + review_id）：______
反例 non-matches（逐字 + review_id）：______
```

- [ ] 纳入标准、排除标准都要写，不能只写一边。
- [ ] 名字与标准是分开的两件事；改名不影响标准判定。

## 五、打分理由、代表样例与反例 non-matches

采用结构化概念归纳方法时，一个主题要同时摆三样东西，别只报个占比：

| 要素 | 作用 |
|---|---|
| `score rationale`（打分理由） | 说清「为什么这条算进这个主题、为什么打这个分」 |
| 代表样例 | 最能代表该主题的几条逐字原句（带 `review_id`） |
| **反例 `non-matches`** | 看着像、但按排除标准**不算**的原句，防止标准被悄悄放宽 |

- [ ] 没有反例的主题定义视为不完整，需补齐后再采纳。
- [ ] 三样都过 grounding check，引用必须能定位。

## 六、小样本 / 0 组 / 未指明桶

- [ ] **小样本警告**：样本不足标「仅供参考」，不给两位小数（分档见 `data-schema.md`）。
- [ ] **0 组显式显示**：某个分组一条都没有，也要把它列出来写 0，不许悄悄删掉让分布显得好看。
- [ ] **「未指明」桶**：版本 / 时长等字段缺失的行，统一归进「未指明」，不丢弃、不猜测填空。

> 这套做法借自 amos2026ss02 的 Demographic Breakdown：绝对计数 + 组内占比 + 小样本警告 + 0 组显示 + Not specified 桶。

## 七、结论后自动追加核查追问

每条结论后面，报告自动附一串核查追问，促使复核者多看一眼。采用公开的审慎核查提示思路，分三类问题：

- [ ] **核查关键事实**：这句能翻回哪条原话？分母是什么？`review_id` 查得到吗？
- [ ] **探查假设**：这里把「推断」当「事实」了吗？有没有偷偷写成因果？
- [ ] **缺失上下文**：是不是漏了某个渠道 / 某个时间窗？「未指明」桶有没有被忽略？

## 八、三段式定义与静态断言

| 段 | 允许出现什么 | 谁产生 |
|---|---|---|
| **数据事实** | 原值、条数、分母、可直接核对的同期变化 | 脚本 |
| **模型推断** | 主题名、纳入 / 排除标准、置信度、聚类结果 | 聚类 + AI，**永远带 `needs_human_confirm`** |
| **运营建议** | 优先级、负责方、验证指标、动作 | AI + 人工确认 |

- [ ] **推断不得混入事实段**：`ur_report.py` 有静态断言——推断段的内容出现在事实段，**直接拒绝出报告**。
- [ ] **AI 起的主题名只是索引不是事实**，不放进「数据事实」段。
- [ ] 报告禁用无来源的精确数字；任何百分比都要能翻回 `count / denom`。

## 九、人工抽检与编码者间信度

- [ ] **人工抽检**：从每个主题抽一批评论，人肉确认「按纳入 / 排除标准，确实该这么归」。
- [ ] **编码者间信度**：多人（或人与模型）各自给同一批评论打标签，用 `Krippendorff's alpha` 量一量彼此对不对得上；对不上就回去修标准。
- `Krippendorff's alpha` 大白话：一个衡量「几个人打标签打得有多一致」的系数，越一致说明主题定义越清楚、越不靠个人感觉。

## 十、负向用例：假 review_id 必须被丢

护栏不能只写在纸上，要有能跑的反向验证：

| 用例 | 输入 | 期望结果 |
|---|---|---|
| 假 `review_id` | 洞察引用一个不存在的 ID | **整条丢弃** + 写审计 + 不进报告 |
| 原句被改写 | 引用句和库里逐字原句对不上 | **整条丢弃** + 写审计 |
| 推断混入事实段 | 事实段塞进一句主题结论 | **拒绝出报告**（静态断言） |
| 填 0 冒充没数 | 变化小于精度却写 0 | 拒绝，改「—」 |

- [ ] 这些负向用例由 `ur_verify.py` 统一跑，`--grounding-check` 必须全绿才算过。
- [ ] 负向用例不通过，不许交付。

## 十一、措辞铁律与借鉴来源

- **只写「同期出现」**，**禁写「导致 / 因为 / 使得 / 由于」**。措辞模板见 `analysis-playbook.md` 第十节。
- 方法来源说明：本文件综合公开的证据核验、结构化概念归纳、人群拆分与核查追问方法，**未复用第三方代码、数据、素材或商业服务**；方法清单在 `analysis-playbook.md` 第一节，“明确不装 / 不部署”清单在 `env-and-risks.md`。
